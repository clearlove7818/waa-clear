# 与独立 tech-doc 协作

`waa-relax-go` 负责中文表达与交互，独立的 `tech-doc-style-chinese` 补充技术文档要求。本文件说明读取条件和风格裁决。

## 必须何时读取

技术文档、产品介绍、中文 Markdown 技术内容、API 说明、操作手册、运维／排查／安全说明和界面文案适用时，必须先按宿主真实发现机制或当前授权路径判断独立 tech-doc 是否可读取。可用时完整读取它的入口，并按入口条件读取适用参考：

| 独立资源 | 分支 |
| --- | --- |
| `references/terminology-and-typography.md` | 术语、错词、大小写、标点、留白、单位、段落换行 |
| `references/api-status-copy.md` | API 状态、错误码、枚举与接口提示 |
| `references/controlled-technical-chinese.md` | 操作、排查、安全、运维、多步 API 流程 |
| `references/project-overrides-example.md` | 用户确实请求建立项目覆盖时，仅作模板，不当现有约定 |

这些路径相对于独立 skill，不是本包内文件。只有 task-authorized 的项目资料可读取；tech-doc 的“检查项目约定”不授予扫描无关文件或写治理的权限。

不可用时继续用本包的完整 STC 改编基线，并在适当回执说明“仅完成 waa-relax-go 基线检查，未读取独立 tech-doc”。不可读、缺文件和权限拒绝分别如实说明；不得安装、假装读过或绕过拒绝。纯对话不必为了引号加载文档专门规则。

技术成品遇冲突按独立 tech-doc 的专门规则；周围中文对话按本包。双方共同的事实、权限、固定字面量保护仍有效，不能用专门风格覆盖高优先级限制。

<a id="quotes"></a>
## 引号：弯引号与直角引号

独立可编辑中文基线（G17）默认弯双引号“”，嵌套‘’；适用且可用 tech-doc 的技术成品默认直角「」，嵌套『』。用户／项目／地区／固定引语约定优先。排版选择不是普遍语言合规证书。

| 同一事实 | 表达 |
| --- | --- |
| 普通对话 | 点击“保存”即可保存草稿。 |
| 技术成品 | 点击「保存」即可保存草稿。 |
| 项目明确保留弯引号 | 仍写“保存”，不按技术默认强改 |
| 固定引文 | 原句使用哪种引号就保留，建议与引文分开 |

实际 checker 分支必须匹配成品：`--style relax-go` 默认 curly；`--style tech-doc` 默认 corner；`--quotes curly`／`corner` 明确项目约定；`--quotes preserve` 不判现有两类引号错误。两类成对引号里的词语提及都保护。一个文件混有普通对话与技术正文时，分别检查选定片段／文件或按共同项目覆盖，不用一个全局 mode 宣称混合文本全部合规。

## 词表：具体表达与真实术语

全量 STC 词条保留，按 [词表用法](../dictionary/README.md#applicability)先判断语境。tech-doc 的官方／项目优先、合法多义词不全局替换原则负责技术成品的专门判断。基线本身也保护真实技术意义，不用两个互斥词典竞争。

| 语句 | 判断 |
| --- | --- |
| “像素对齐能避免图标边缘模糊。” | 实际技术意义保留；效果需来源支持 |
| “会前先对齐口径。” | 确指统一说法时改“会前先统一对外说法” |
| “采用闭环控制。” | 解释反馈机制，不一律改“完整流程” |
| “赋能团队。” | 正式名称例外不等于免检空话；缺对象／能力时待确认，不编实际效果 |
| “删除后可撤销。” | 按产品恢复事实保留，不为词典“永久”改成无法恢复 |
| “不是超时，而是权限不足。” | 若有证据是有用区分；可分成“未发生超时。当前账号权限不足”，不删对比或编原因 |

检查器保留词表／规则 ID、位置、例子方向和真实候选；`--style tech-doc` 把命中明确标为技术语境建议。全部语义依赖词语在两种 mode 下都是 warning，不用一个狭窄正则白名单无声吞掉“对齐”等命中。它不能判断项目术语表、因果或事实真假。保留候选与 context 提示比自动改写或硬失败安全；明确固定模态混用也需人工判断原强度。

## 人称、篇幅和结构

- **主体：** 对话 C1 可用“我”“你”；技术正文默认无主句或“开发者”“管理员”等中性角色。界面第二人称是项目风格，可按专门规则覆盖；不以词语存在宣称主体错误。
- **句长与分组：** 40 字句子、30 字步骤、3 层修饰、约 5 项分组是帮助检查主干的推荐，不删除完整参数、全部条件、七步流程或相关选项。checker G12 只警告。
- **操作与原理：** 真实多步操作按 A2／D5 编号，条件与风险先行；概念说明、产品介绍和已明确请求的解释不用伪操作清单。确实同时或不可分的操作可按独立规则同一步。
- **回执与正文：** C10 的结果／用户动作／知会属于交付对话，完整三段可选。文档正文不附“下一步你做……”或会话状态，也不填回执空标题。

## 风险与任务模式

安全、数据、权限、恢复与不可逆后果依实际机制命名。警告／注意／说明按真实风险；“删除”“失败”“取消”不自动证明永久丢失、零副作用或原因。缺信息标待确认，不补重试时限或强制 onboarding。空状态先分未创建、过滤、无权限、加载失败。

撰写、改写、校对、审阅严格分开：校对只改约定错字／排版／术语，不扩成结构和语气重写；审阅先报告，不自动改文件；已获授权改写可直接在边界内执行。明确请求 STC 风格审计时，可单独报告基线 findings 与技术风格 findings，不能悄悄重写本应遵循 tech-doc 的成品。

<a id="spacing"></a>
## 字面量、留白与段落

只处理可编辑的可见中文。行内代码、围栏代码、URL／链接目标、JSON、API 路径、数据库字段、命令、官方名称和固定引语保持原样。可见正文中西文、阿拉伯数字和版本号之间留一个半角空格；只在标记外侧处理，不把空格插进 URL 或命令。

技术 Markdown 正文一段一行，编辑器软换行阅读；不为源码宽度硬折行。标题、列表结构、表格、代码、引用原文、HTML 和显式换行保持结构。若任务只校对标点，不因此批量合并段落。检查器不附硬换行写入工具，也不读取独立包工具，不声称覆盖这些全部专门规则。

示例（机器内容不变）：

```markdown
运行 `tool --mode=read`。响应字段为 `result_id`，接口路径为 `/v1/jobs`。
```

## 检查器不替代独立规范

检查器的 `--style tech-doc` 提供引号与用词提示。API 状态、段落格式、事实语义和实际呈现必须结合独立 tech-doc 的适用参考人工复核。参数见[工具说明](../tools/README.md)。
