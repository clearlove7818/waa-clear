# 通用规则 · for-all

通用规则，四个场景都必须完整读取并应用。场景规则补充本文件；事实、权限、技术含义、固定文本和用户／项目约定始终优先。技术成品的专门风格裁决见 [tech-doc 协作](../references/tech-doc-compatibility.md)。

本文件包含 G1–G22 的用法、原因与例子。例子是构造演示，其中的名称、数字、原因、恢复方式和时限只有在实际资料支持时才能使用。

## 用词

<a id="g1"></a>
### G1 一个意思只用一个词

同一份文字里，同一个东西、同一个动作必须只用一个首选叫法。确实不同的技术动作不得因词近义而合并；官方名称、界面固定标签和用户原话保留准确写法。

原因：同义词换着用，读者会以为说的是几样不同的东西。大模型为了显得用词丰富，常常轮换同义词。

- ✗ 上传前，系统先校验文件格式，检查通过后再核对文件大小。
- ✓ 上传前，系统先检查文件格式，再检查文件大小。

<a id="g2"></a>
### G2 产品名、功能名、指标名照项目术语表写

用户提供或当前授权材料明确包含术语表时，必须照表里的名称和含义写，不得另造近义叫法。没有术语表时，沿用可靠上下文、产品官方名称和已有叫法；有歧义则标明待确认。缺表不构成扫描无关文件、新建或修改治理文件的授权。

原因：项目术语表让各处名称可互相识别；强行补表会把表达任务扩成配置任务。模板保留全部 3 个示例条目，只有用户请求模板时读取 [`terms.example.yaml`](../dictionary/terms.example.yaml)，实际创建仍以任务授权为准。

- ✗ 导航里叫“项目”，帮助文档里叫“工程”。
- ✓ 导航和帮助文档都叫“项目”。

<a id="g3"></a>
### G3 用推荐词，按语境处理不推荐写法

必须读取全部 [`avoid.yaml`](../dictionary/avoid.yaml)，逐条按 `profiles` 选择：未写或为空适用于所有场景；包含当前场景才在该场景使用。适用推荐词时，必须读取全部 [`recommended.yaml`](../dictionary/recommended.yaml)，宜使用表中明确的动作和区别。完整字段、例子与裁决见 [词表用法](../dictionary/README.md)。

先判断是否真有该条指出的含糊、冗余或强度问题，确认后才按推荐方向修改。技术术语、项目定义、事实对比、原文引用和保护内容优先；词表是用法约定，不是产品行为事实。不得凭词表补造数字、原因、权限、不可逆性或扩大对象范围。缺依据的歧义报告为待确认，不直接替换。

原因：一个词的约定含义帮助区分动作，但关键词不能证明上下文。推荐的“删除”例句描述不可恢复的演示产品，不表示任何名为“删除”的操作都不可恢复。

- ✗ 把“像素对齐”一律改成“像素确认”。
- ✓ 图标需要像素对齐。（确有技术含义，保留）
- ✓ 会前先统一对外说法。（“对齐口径”确指统一时）
- ✓ 任务材料明确支持撤销时：删除后可在回收站恢复。

<a id="g4"></a>
### G4 动作直接写成动词

可编辑中文里的虚动词结构“进行、加以、予以、作出、开展”加动作名词，必须改为直接的动词；若是固定引用、术语或实际状态（如“进行中”），保持原样。保留动作对象和原有责任主体。

原因：这类结构让句子变长，还把动作藏进名词，读者要多想一步才知道做了什么。

- ✗ 对数据进行分析。
- ✓ 分析数据。
- ✗ 对配置作出调整。
- ✓ 调整配置。

<a id="g5"></a>
### G5 程度词和模糊量词换成有依据的数字或具体事实

程度词和模糊量词掩盖了任务所需的程度、对象或范围时，必须用已有依据的数字或具体事实说明。常见的有“非常、极其、大量、显著、大幅、基本、一些、部分、若干、相关”。没有数字或事实时，不得编造，也不得从词表例句借来事实。

草稿可使用“【待补：…】”，并在稿后列出全部缺项；普通对话可直接说明数量、范围或程度未知。删掉无依据的强调词时，不得新增肯定结论。“显著改善”缺证据时，不得改成“已改善”并声称核实。原文已有的有意义定性观察可保留并注明依据局限；G15 的真实不确定性不属于删改对象。统计术语“显著”、章节名“部分”、数学“相关”先按技术含义判断。

原因：读者无法从“大量”知道是多少，也无法从“显著”知道变化有多大。编出来的数字会被读者当成事实。

- ✗ 显著缩短了加载时间。
- ✓ 加载时间从 3 秒缩短到 1 秒。
- ✓ 原文已提供缩短这一事实、只缺幅度时：加载时间缩短了【待补：缩短前后的秒数】。
- ✗ 请准备相关材料。
- ✓ 请准备营业执照和法人身份证。
- ✓ 所给反馈仅说明有人无法登录时：反馈称有人无法登录，受影响人数未知。
- ✓ 仅有“非常快”这一主张且未测试时：原文称处理较快；实际耗时尚未核实。

<a id="g6"></a>
### G6 不用不增加信息的营销词和套话

必须删去删后意思不变的营销词、空泛行话和套话。常见的营销词有“赋能、一站式、无缝、极致、打造”；常见的行话有“沉淀、落地、对齐、闭环”；常见的套话有“值得注意的是、综上所述、众所周知”。事实不明时说明缺口，不凭改写补成具体效果。

这些词有真实技术或业务含义时，必须先确认含义再判断：化学沉淀、像素对齐、闭环控制、网络链路、数据颗粒度可保留，首次解释读者不熟悉的术语。正式名称和固定引用保持原样。不得把整句含糊宣传藏在“技术词”例外里；即使保留术语，也须检查对象、动作和依据是否清楚。

原因：空泛使用这些词不增加信息。未解释的行话还要求读者先翻译成具体动作才能理解。

- ✗ 值得注意的是，该方案能无缝赋能各个业务线。
- ✓ 该方案适用于全部 4 条业务线，不用改现有流程。
- ✓ 控制器使用闭环控制：传感器反馈实际温度，控制器据此调整加热功率。（资料支持此机制时）

<a id="g7"></a>
### G7 不用代替事实的口号句式

不得用“不是 X，而是 Y”式空泛宣言、对仗金句或顶针句代替事实。需要对比时，宜拆成两句平实的话；有用的排他判断、纠错或事实对比必须完整保留，不按句式关键词删除。“不是认证失败，而是权限不足”若有证据，是诊断区别，不是口号。固定引语或用户指定修辞保持原样，另列建议。

原因：口号句式读着有气势，但没有说清事实。读者要的是机制、数字和依据。

- ✗ 交付的不是工具，而是结果。
- ✓ 交付物是每月一份数据报告和一份改进清单。
- ✓ 身份认证已通过。当前账号缺少读取权限。（仅在证据支持时）

<a id="g8"></a>
### G8 缩写和代号第一次出现时附全称或解释

缩写、产品代号、内部代号第一次出现时，必须附上全称或一句解释。不得自造缩写。

原因：读者可能不知道内部简称；就地解释比让读者回查前文更可靠。解释不得改写机器标识或猜测未知全称。

- ✗ 本周 CR 通过率下降。
- ✓ 本周代码评审（CR）的通过率从 80% 降到 65%。

## 句子

<a id="g9"></a>
### G9 一句只讲一件事

一句必须保留一个清晰主干。超过两个独立动作或判断时，宜拆成几句；三项以上独立并列宜写成列表。完整条件、必要因果、不可分操作和固定原文优先，不为计数拆坏关系。真正操作流程按场景 D5 与交互 A2 编号，一步一个边界明确的动作。

原因：一句话塞进几件事，读者容易漏掉中间的那件。

- ✗ 上传文件后系统会检查格式并生成预览，同时通知审核人，审核通过后自动发布。
- ✓ 上传文件后，系统检查格式并生成预览。系统同时通知审核人。审核通过后，系统自动发布文件。

<a id="g10"></a>
### G10 条件写在前面

条件宜写在前面：“如果……，……”“……时，……”。

原因：读者先知道条件，才能判断后面的内容是否适用于自己。

- ✗ 删除后其他人也打不开这个文件，如果文件已经共享。
- ✓ 如果文件已经共享，删除后其他人也打不开这个文件。

<a id="g11"></a>
### G11 用主动句

宜用主动句。“被”字句只用在不需要说明是谁做的时候。

原因：主动句写清了谁做了什么。中文的“被”字句还常带不情愿、受损的意味。

- ✗ 配置被管理员修改了。
- ✓ 管理员修改了配置。

<a id="g12"></a>
### G12 控制句子长度

一句话宜不超过 40 个字；操作步骤的一句宜不超过 30 个字。

说明：字数按汉字计，英文单词、数字各按一个字计。40／30 是可读性推荐，不是上限或事实截断门槛。句子过长时先按 G9 检查主干；必要条件、完整解释、固定文本和任务要求优先。检查器仅给超过 40 的警告，不能证明步骤完整或句意正确。

原因：短一些的句子更便于定位动作；机械截断会漏掉条件和否定。

- ✗ 为满足 30 字删去“仅管理员”和“审核通过后”。
- ✓ 审核通过后，仅管理员可发布报告。（保留完整条件和权限）

<a id="g13"></a>
### G13 名词前的修饰语宜不超过 3 层

名词前的修饰语宜不超过 3 层。修饰语过长且影响理解时，宜拆成主句加补充说明。3 层是提示，不改变专有名称、必要限定或固定引用。

原因：多层修饰会让读者找不到核心对象；拆开后必须仍能知道限定的是哪一个对象。

- ✗ 已配置好的高优先级每日自动同步任务失败了。
- ✓ 每日自动同步任务失败了。这个任务已配置好，优先级为高。

<a id="g14"></a>
### G14 否定词和限定词不省略

否定词和限定词不得省略，也不得弱化：不、没、未、无、非、仅、只、除外。

数字、单位、专业术语、代码标识、命令、接口名和错误原文必须保留准确写法。用户明确要求且当前任务已授权这些内容的改动时，按原任务处理；仅风格润色不授予改机器字面量的权限。

原因：少一个“不”或“仅”，意思就反了或变宽了。压缩文字时最容易丢掉这类词。

- ✗ 管理员可以删除。（原意是只有管理员可以删除）
- ✓ 仅管理员可以删除。

<a id="g15"></a>
### G15 保留表示把握程度和频率的词

表示把握程度和频率的词必须保留：可能、也许、大概、通常、偶尔、经常。没有把握的判断不得写成确定的结论。这些词是内容，不按 G5 删改。

原因：把握程度本身是内容。把“可能失败”改成“失败”，结论就变了。

- ✗ 请求失败是网络中断导致的。（实际只是推测）
- ✓ 请求失败可能是网络中断导致的。

<a id="g16"></a>
### G16 代词只指上文里明确的名词

代词和指示代词（“它、这、该、其、此”）必须只指同一句或上一句里出现的名词。可能指两个以上的对象时，必须重复名词。

原因：读者不必猜测代词的对象；段落转发或恢复任务时也能定位对象。场景 D1、W1 对可独立出现的文字进一步要求明确名称。

- ✗ 上传图片和视频后，系统会压缩它。
- ✓ 上传图片和视频后，系统会压缩图片。

## 标点与数字

<a id="g17"></a>
### G17 标点与引号按适用约定统一

STC 以 GB/T 15834—2011《标点符号用法》为标点参考。本技能独立、可编辑的横排中文默认使用弯双引号“”，嵌套用弯单引号‘’。用户、项目、地区或固定引用约定优先；原引语不因本规则改动。

技术／产品／界面成品适用且独立 tech-doc 可用时，按其直角引号「」和嵌套『』写；周围对话仍用本技能默认。必须按 [协作裁决](../references/tech-doc-compatibility.md#quotes)处理，不能把弯引号等同于普遍合规。检查器 `--style tech-doc` 接受直角引号；`--quotes curly|corner|preserve` 可表达项目覆盖。两类引号内的提及都不做词表替换，实际固定引语另行保护。

原因：排版统一帮助识别引用和控件；不同写作约定不应互相覆盖或破坏固定文本。

- ✓ 独立基线：点击“保存”后，页面显示“已保存”。
- ✓ tech-doc 成品：点击「保存」后，页面显示「已保存」。
- ✓ 项目保留引用：原句为「请选择『保存』」。

<a id="g18"></a>
### G18 数字照 GB/T 15835—2011

数字必须照 GB/T 15835—2011《出版物上数字用法》使用：计量和统计用阿拉伯数字，数字后写单位。

原因：数字和单位一起让数量可核对。保护原有精度、范围、比例、版本和固定名称；不为统一样式换算单位、补年份或把百分比改成百分点。

- ✗ 共计三百二十个样本，耗时约两个小时。
- ✓ 共 320 个样本，耗时约 2 小时。

<a id="g19"></a>
### G19 中文与英文、数字之间空一格

中文与英文、数字之间宜空一格。项目可以另行规定，但同一份文字必须统一。

原因：留白帮助区分文字和数值。只处理可见中文边界，不改代码、URL、字段内部或官方拼写。技术成品的行内代码、单位、链接显示文字与段落换行处理见 [tech-doc 协作](../references/tech-doc-compatibility.md#spacing)。

- ✗ 共320个样本，用AI生成。
- ✓ 共 320 个样本，用 AI 生成。

## 内容

<a id="g20"></a>
### G20 Anti-Echo：只写当前读者需要的内容

每句话必须帮助当前读者理解内容、判断或完成操作。读者未问、也不影响这三件事的说明，必须删除。

交付前必须逐句检查以下内容：

- 排除读者没有想到的内容，或解释未采用的方案。
- 汇报制作过程、规则选择、检查动作或设计意图。
- 给成品附加施工标签、占位说明或结尾自证。
- 复述标题、控件或当前页面已经表达的意思。

判断时必须结合任务和读者，不能只按关键词删除。价格范围、权限限制、不可逆后果和影响事实理解的图例必须保留。用户明确要求的比较、过程说明和审计记录，必须按请求提供。

保留疑似多余内容时，必须说明删掉后会造成的具体误解、错误操作或未满足的要求。不能只用“安全”“合规”这类类别作为理由。能用工具核对的前提，必须先核对。例如当前页面已显示的归档、停用或错误状态，不必再重复说明。

用户要求删除某项内容时，必须删除对应说明，不得换成近义词重新写回。不得为此改名或隐藏接口、测试和诊断记录。变更说明必须以定稿或发布版本为基准。用户原有内容和要求的比较记录，必须按任务需要保留。

交付文字必须从当前采用的结果写起。未要求且不影响判断的方案取舍和制作过程不放进正文；任务已经授权过程记录时，依据放在该记录里。用户要求比较、证据或过程时，必须按请求交付，不把必要内容藏到内部。检查后文字又有变化时，必须重新检查实际定稿。

对外正文、按钮、提示、图注和页面角标必须分别检查；不能渲染时，说明表面审阅未验证。不得为记录每条聊天回复而新建文件；只用已授权的过程记录。命令检查通过后，仍须审阅句子是否必要。

原因：无关排除和自证让读者找不到结果；但真实边界决定能否正确理解和操作，不能一并删去。

- ✗ 午餐：西红柿炒鸡蛋（没有东坡肉）。
- ✗ 午餐：西红柿炒鸡蛋，没有东坡肉。
- ✓ 午餐：西红柿炒鸡蛋。
- ✗ 页面已完成，已确认没有旧版内容。
- ✓ 页面已完成。
- ✗ 在产品首页流程图旁写“诊断流程示意”，仅用于说明这张图的制作意图。
- ✓ 删除该标签；保留说明实际步骤和结果的文字。
- ✓ 报价 1200 元，不含税。
- ✓ 产品确实没有恢复能力时：删除后无法恢复。
- ✓ 演示而非真实数据时：示例数据，仅用于说明报表格式。
- ✓ 虚线表示估算值，实线表示观测值。

机器检查将疑似内容标为 G20 待复核项。使用 `--anti-echo` 时，疑点必须改写，或在已有授权的审稿资料中记录与当前原文绑定的保留理由，才能通过。理由必须说明删掉后会造成的具体误解、错误操作或未满足的要求。检查器能核对绑定和非空理由，不能证明理由充分；文字变动后旧决定失效。格式见 [只读检查器](../tools/README.md#anti-echo)。

<a id="g21"></a>
### G21 用自然的完整句子

必须使用读者熟悉的词和自然语序，保留完整语法。句子和段落的长短必须随内容变化，不得为凑节奏添加情绪、故事或口号。朗读时拗口、定语过长或主语不清的句子，必须改写。

事实、名称和真实的不确定性必须保留。需要说明判断时，必须给出依据，不得为让表达有个性而编造经历或观点。

原因：只剩关键词会丢掉主语、条件和关系；自然句子仍须直接而完整。

- ✗ 研发组下周将针对导出功能进行进一步的测试。
- ✓ 研发组下周测试导出功能。
- ✗ 无法删除。只读。管理员。
- ✓ 只读成员不能删除文件。请联系管理员。

### G22 篇幅由任务需要决定

默认必须删除客套、重复、空话和不影响使用判断的解释。用户要求完整文稿、详细解释或操作步骤时，必须交付所需内容。不得用固定字数、句数或压缩比例代替任务要求。

复杂步骤、权限限制和不可逆后果必须写完整。用户问到的例外必须解释清楚。信息已经足够时，必须停止，不再追加总结、保证或无关内容。

原因：简短服务任务，不替代任务。长解释、七步流程、完整选项和真实风险不能被 40 字、300 字或 5 项建议截断。

- ✗ 用户要三步操作，只回复“点导出”。
- ✓
  1. 打开“报告”。
  2. 选择要导出的报告。
  3. 点击“导出”。
- ✗ 用户只问导出按钮在哪里，回复一份完整的功能介绍。
- ✓ “导出”按钮在报告页右上角。
