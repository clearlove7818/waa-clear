# 文档规则 · for-document

适用于给人读的文字：报告、方案、说明、手册、会议纪要，以及给开发者看的代码注释、提交说明和日志。读者读这些文字，是为了理解内容或照着操作。

通用规则（[`for-all.md`](for-all.md)）同样适用。

必须完整读取本文件及 [推荐词表](../dictionary/recommended.yaml)。技术成品适用时按 [tech-doc 协作](../references/tech-doc-compatibility.md)读取独立专门规则。例子是演示，不提供用户材料的事实、风险、时限或根因。

<a id="d1"></a>
### D1 主语写名称，不写含糊人称

文档主语必须可独立识别，默认写公司名、品牌名、人名、职务或对象名，不用含糊的“我们”“你们”“他”“她”“它”；表头和分工表同样适用。主语是作者或作者团队且不混淆时，可省略，比如周报“本周上线了导出功能”。固定引用与项目明确文体保留；技术成品默认中性角色，按 tech-doc 专门规则处理，不把对话“你”写进正文。

原因：文档会被转发，读的人不一定知道“我们”指谁。

- ✗ 表头：“我们负责”“你们负责”
- ✓ 表头：“供应商负责”“客户负责”

<a id="d2"></a>
### D2 先写结论，再写依据

必须先写结论，再写依据。每一节的第一句宜写这一节的结论。

原因：读者可先判断该节用途，再按需核对证据。结论没有依据时，先说可确认范围或缺项，不编造确定判断。

- ✗ 本季度共收到 120 条反馈。其中 45 条与加载速度有关……综合来看，加载速度问题要优先处理。
- ✓ 本季度优先处理加载速度问题。依据：120 条反馈里有 45 条与加载速度有关，占 38%。

<a id="d3"></a>
### D3 一段只讲一个主题

一段必须只讲一个主题，一段宜不超过 6 句。

原因：读者能按主题回看。6 句是组织建议，必要定义、条件和完整解释优先；技术 Markdown 一段一行，不用源码硬换行凑短句。

- ✗ 同一段混写接口定义、价格和部署历史。
- ✓ 定义接口后，另段说明适用范围。

<a id="d4"></a>
### D4 三项以上用列表

三项以上独立并列内容必须整理成列表；真实多步操作无论是否满 3 步，都用编号列表（交互 A2）。概念解释可用自然段，不强制伪造操作。完整七步流程保留全部 7 步，长列表按主题分组而非隐藏第 6 项以后。

原因：并列项可逐项核对，编号能识别执行顺序。

- ✓ “前置条件”“步骤”“恢复方式”分别组织，不夹在一个长句里。

<a id="d5"></a>
### D5 操作步骤一步一个动作，说明与步骤分开

操作步骤必须一步写一个动作，每一步以动词开头。说明和提醒必须与步骤分开写，说明里不得夹带要求。

必须保留前置条件、必要确认、失败时的停止条件与已有恢复方式。系统自动行为写成说明，不变成人工操作。两个同时动作确实不可分时按专门技术规则保留，不为少步骤合并顺序动作。

原因：一步一动作让读者知道停在哪一步；把要求藏在“说明”里会漏执行。

- ✗ 打开设置并点击账号，修改邮箱，注意新邮箱要能收信。
- ✓
  1. 打开“设置”。
  2. 点击“账号”。
  3. 修改邮箱地址。
  4. 打开新邮箱里的验证邮件。
  5. 点击验证链接。

  说明：验证完成前，登录仍使用原邮箱。

<a id="d6"></a>
### D6 风险提示先写动作或条件，再写后果

风险提示必须先写要做的动作或触发的条件，再写不照做的后果。

原因：用户必须在执行前知道后果。恢复能力必须来自实际产品资料；“删除”这个词不证明永久丢失，不得虚构“无法恢复”。

- ✗ 请注意数据安全。
- ✓ 资料确认不可恢复时：删除前先导出数据。删除后，数据不能恢复。
- ✓ 资料支持回收站时：删除后，文件移入回收站；可在保留期内恢复。（保留期未知就不补天数）

<a id="d7"></a>
### D7 提醒分三级：警告、注意、说明

需要提醒读者的内容，必须按风险大小用三个固定的词开头：

| 词 | 用在什么时候 |
|---|---|
| 警告 | 继续操作可能造成数据丢失、安全问题或无法撤销的结果 |
| 注意 | 继续操作可能失败，或结果不符合预期 |
| 说明 | 补充背景、定义或依据 |

- ✗ 温馨提示：删除后无法恢复哦。
- ✓ 警告：删除后，数据不能恢复。

该例只适用于确认不可恢复的产品。原因：级别表达真实后果，不是装饰标签；缺后果证据时列为待确认，不从词典反推。推荐词表的警告／注意／说明区别必须结合实际语义应用。

<a id="d8"></a>
### D8 代码注释写原因，提交说明先写改了什么

代码注释必须写为什么这样做，不得复述代码在做什么。提交说明的第一行必须写改了什么，正文写为什么改。

原因：代码已经表达动作；维护者需要知道约束与原因。注释和提交草稿只在任务要求时写，不因此获得提交权限，原因未验证就标明假设。

- ✗ `// 遍历列表`
- ✓ `// 跳过已删除的记录：接口返回的数据里仍包含已删除的记录`
- ✗ 提交说明：“修改了一些问题”
- ✓ 提交说明：“修复导出表格时日期少一天的问题”，正文写原因：时区按 UTC 计算。
